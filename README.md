# Real-world data task blueprints: ETL build problems and analytical stumps

Task blueprints for evaluating data and analytics work. Every blueprint describes a real project and a decision that resolves
to **one deterministic recommendation**, the wrong paths a capable solver takes, the deliverables, and where a rubric of 25+
criteria comes from. Set 1 blueprints are built on real, licence-clean public files. Set 2 notes are stump designs: the idea
and driving force of each stump, with the numbers a generated data pack must hit.

## Shared standards

* **One deterministic recommendation** per task.
  * **Set 1** fixes it with a written memo of rules that ships with the inputs.
  * **Set 2** fixes it by construction: filed pins, a calibration corpus, and conventions that are pinned or converge. The
    decisive rule itself is never stated.
* **One to three deliverables**, preferring a visual from which the stakeholder can read the decision at a glance.
* **25+ rubric criteria** derived from the structure of the answer, weighted roughly 30–40% on the recommendation, 5–10% on
  instruction following and about 55% on the supplementary asks.
* **Difficulty target:** a model average below 50%, with at least one strong model stumped.
* **Inputs:**
  * **Set 1** blueprints rest on real, licence-clean public sources; nothing is generated by a language model. Packages list at
    least 10 files in at least 3 formats, with at least one file of 10,000+ rows.
  * **Set 2** notes carry the stump design only. The data pack is generated to each note's world-building constraints and
    sized to the same input bar when the task is built.
* **Honest data:** every number a solver reads is correct and documented. Nothing is planted, and the retired "flip the wrong
  number" defect is never used.

## Set 1 — Data extraction, conformation & ETL build problems (50 tasks)

Fifty task blueprints built from pain points that data-engineering, ETL and data-conformation teams hit in production.
Each one is a real project, a decision that resolves to **one deterministic recommendation**, and a trap that a
competent solver falls into because something documented was overlooked — a key that is *n + 1* columns, a delta file
whose status column was ignored, a calendar with a 53rd week, a crosswalk that is many-to-many, a unit that changed on a
filing date.

Every trap is an **honest-data** trap: the source data are real, correct and documented. Nothing is planted. The
difficulty comes from method selection, grain, time semantics, identity resolution, reconciliation, or a binding
definition the solver must apply as written.

### What is in each file

Every `problems/Pxx_*.md` file has the same twelve sections, so it can be turned into a task directly:

1. **The real-world project** — who is building what, and how it went wrong the first time.
2. **The business decision** — the one deterministic call, plus the written rules (the "standard/method/protocol" memo
   that goes in the task folder).
3. **Why this gets overlooked** — why capable teams miss it in practice.
4. **Input package** — ≥ 10 files, ≥ 3 formats, at least one file with 10,000+ rows, each with source and licence.
5. **Deterministic solution path** — the single correct method, step by step.
6. **The traps** — each wrong path, why it is tempting, and what it does to the answer.
7. **Why the data is honest** — why this is not a retired "planted defect" trap.
8. **Draft task prompt** — prose, the way you would ask a colleague.
9. **Deliverables** — one to three files across data / visual / text / code families.
10. **Where 25+ rubric criteria come from** — the structure of the answer that generates the rubric.
11. **Golden-output checklist** — what a correct answer must contain.
12. **Build notes** — how to scope the slice so the trap actually flips the recommendation, and what to verify.

`problems_index.csv` lists all fifty with domain, objective family, task shape, core technique, trap family and sources.

### Before you ship a task from a blueprint

* **Download and freeze the inputs.** Record source URL, download date, and licence for every file. Several sources are
  live (OpenFEMA, CFPB, NPPES, BDC, AACT, Inside Airbnb); answers change between downloads.
* **Verify every field name, code value and threshold against the documentation you ship.** The blueprints name fields
  and rules as they are documented to the best of current knowledge; agencies rename columns and revise rules. Where a
  blueprint says "verify", treat it as a required check, not a suggestion.
* **Compute both the correct path and each trap path before freezing the prompt.** Section 12 of every file says how to
  pick the slice (state, year, entity set, cap) so the trap changes the recommendation. If it does not flip on your slice,
  change the slice — do not change the data.
* **Write the method memo yourself, from the rules in Section 2.** It is the only authored document in the package; every
  other input should be a real, licence-clean public file.
* **Keep the deliverables to one to three files** and prefer a visual where it lets the stakeholder read the decision at
  a glance.

## Set 2 — Analytical stumps (300 tasks)

Three hundred stump designs, fifty in each of six analytical categories. Each mirrors a problem that analytics, data-science
and operations teams face at large companies: growth, ranking and integrity metrics at consumer platforms; capacity,
reliability and cost in cloud and networking; yield and supplier quality in hardware manufacturing; pricing, risk and
fulfilment in marketplaces, finance and supply chains. The `Mirrors` row of every file names the company problem it stands
for, and every task sits in one of six domains.

**A note is the idea, not the data.** Each file specifies the decision and the committed call, the driving force of the stump
(the property that makes a strong solver take a plausible wrong path), the ladder of defensible wrong answers, why the
decisive move survives a strong solver, and the numbers a data generator must hit. No dataset is named or shipped. The data
pack is generated to Section 12 of the note when the task is built.

**The stump is analytical, never a defect and never a misreading.** The notes are designed against a solver that:

* reads every document and implements every clause;
* reconciles every control total;
* back-tests every corpus it can sweep;
* builds per-row pipelines flawlessly;
* cleans anything with a symptom.

Every note meets these rules:

* **Gate G.** Every number in the pack is correct and no stakeholder's reading is overturned. The difficulty is a
  construction the decision needs. Every note carries `surface_read_dependency: no · stumping_family: analytical_non_defect ·
  sole_data_defect: no`. A planted defect is never the mechanism, and neither is a single change of lens on the same
  population at the same moment.
* **The clean-data test.** Every incomplete, optional, suppressed, stale or narrower-meaning file that the ladder touches is
  repaired on paper at three depths:
  1. fill the gap;
  2. correct the semantics;
  3. replace the instrument with one that records the decision's attribute directly.

  After the repair, three things must hold:
  * the answer is unchanged;
  * no lower rung lands on it;
  * the decisive construction is still needed.

  Recovering a latent attribution, bounding a suppressed cell or locating an unlocated record may be a lower rung. It is
  never the decisive one.
* **The ladder.** Three to five rungs. Rung 0 is the natural competent pipeline; each later rung names a different candidate
  or figure, dies to exactly one shipped fact, and is a place a careful analyst would stop.
  * **Name answers:** the answer ranks 4th or 5th at rung 0 and never leads an intermediate rung. It wins on discriminator
    dominance, with its decisive edge at least 1.3 × 1.2 × the advantage the runner-up carries in.
  * **Figure answers:** the answer is the extreme cell, or it reverses the walk, and every other cell sits 8–10% or more away.
  * **Partial applications:** no half-applied construction lands on the answer.
* **The seven survival properties** of the decisive move:
  1. It is written in no shipped sentence.
  2. No sweepable corpus nominates it. Either the corpus is blind to it for a computable reason, or reproduction pins a
     construction rather than a menu.
  3. It has no arithmetic symptom.
  4. It is not a per-row predicate.
  5. Its enumeration is arithmetic.
  6. It has no cutover date.
  7. It is still hard after every voice and wrong number is deleted.
* **Calibration corpus and twin pair.** Every note has a closed record that certifies the shallow rungs. It also has a twin
  pair: two cases identical on every visible column, with outcomes about 2× apart, separated only by the right rule.
* **Pins, voices and determinism.**
  * Filed pins fix a basis or scope, never the answer.
  * Voices hold beliefs, never figures.
  * A licensed wrong basis is present.
  * Every convention an analyst could vary is either pinned or shown to converge.
* **Asks and rubric.** At least two device-carried asks, decoupled from the main call, plus one validity ask. A device is a

### Where the decisive moves come from

Each decisive rung instantiates one mechanism from a catalogue drawn from measured failure modes of strong models. Each task's
own property, join or corpus brings the mechanism to life.

* **Rules recovered from closed records:**
  * a control set that only one construction reproduces;
  * finer controls that separate constructions a salient control cannot;
  * minima over sub-units;
  * mixtures in place of constants;
  * self-referencing rules solved to their fixed point;
  * saturated ties broken by the standard's own rule;
  * effects measured from logged natural experiments.
* **Units and grains:**
  * the unit the decision funds, which no file stores;
  * two flawless grains that disagree in shape;
  * segments that must stay fine or be split through a join;
  * implicit joins across complete records;
  * the population a flag only suggests;
  * answers at a grain no monitor expresses.
* **Time and populations:**
  * corpora blind to the decisive rung for a computable reason;
  * past exceedance against forward yield;
  * maturity;
  * continuity across a closure;
  * residual populations between two correct records;
  * a rate validated on one population and applied to another;
  * a correct share carried onto a different book.
* **Objectives and constraints:**
  * the serviceable share behind a join;
  * caps that do not commute;
  * binding limits applied in the figure;
  * admissible options off the offered slate;
  * conditioned yields;
  * counterfactual baselines for causal verbs;
  * the deciding comparison;
  * a quiet second trap behind a loud one;
  * holds forced by a computed blocking quantity.

Latent attribution markers and suppressed-cell bounds appear only below the decisive rung, as the clean-data test requires.

### Uniqueness

* **300 distinct projects.** Each task keeps its own business scenario, entities and numbers.
* **Repeated mechanisms are instantiated differently.** Where a mechanism recurs, it runs on a different property, join or
  corpus. Within each batch of 25, no two tasks share a combination of decisive mechanism, calibration form and decision shape.
* **Nothing is copied.** Driving forces and ladders were checked pairwise for similarity. No scenario, entity, number or
  sentence is copied from the design reference or between tasks.

### Building a task from a note

* **Generate the pack to Section 12** and assert every split, margin, separation and twin-pair fact the note lists.
* **Run the clean-data test in the generator.** Repair each suspect file, recompute, and assert that the answer and every
  lower rung still return what the note says.
* **Reproduce every rung, every partial application and every grid cell** from the generated pack, and keep the
  separations the note requires.
* **Write the prompt from Section 9.** No sentence may fix the basis, window, population or method, and none may name an
  input file or the trap.
* **Score with the Section 11 rubric** at the target weights.
* **Measure before you trust.** Every design is untested against a model until it is run. Treat a note as a blueprint and
  measure it.
