# Real-world data task blueprints: ETL build problems and analytical stumps

Task blueprints for evaluating data and analytics work on real public data. Every blueprint describes a real project, a decision
that resolves to **one deterministic recommendation**, an input package of real, licence-clean public files, the single correct
method, the wrong paths a capable solver takes, the deliverables, and where a rubric of 25+ criteria comes from.

| Set | Folder | Tasks | Index | Where the difficulty comes from |
|---|---|---|---|---|
| 1 · Data extraction, conformation & ETL build | [`problems/`](problems/) | 50 (P01–P50) | [`problems_index.csv`](problems_index.csv) | Honest-data traps in keys, grain, time semantics, crosswalks, units and supersession |
| 2 · Analytical stumps | [`analytical_tasks/`](analytical_tasks/) | 300 (six categories × 50) | [`analytical_tasks_index.csv`](analytical_tasks_index.csv) | A plausible but wrong analytical or methodological path — never a misreading |

## Shared standards

* **One deterministic recommendation** per task, fixed by a written memo of rules that ships with the inputs.
* **One to three deliverables**, preferring a visual from which the stakeholder can read the decision at a glance.
* **25+ rubric criteria** derived from the structure of the answer, weighted roughly 30–40% on the recommendation, 5–10% on
  instruction following and about 55% on the supplementary asks.
* **Difficulty target:** a model average below 50%, with at least one strong model stumped.
* **Inputs:** every blueprint rests on real, licence-clean public sources; nothing is generated by a language model. Set 1
  packages list at least 10 files in at least 3 formats, with at least one file of 10,000+ rows. Set 2 blueprints centre on the
  stump — the mechanism that drives a capable solver down the wrong path — and name the public sources it rests on; the package
  is sized to the same bar when the task is built.
* **Honest data:** the source data are real, correct and documented. Nothing is planted, and the retired "flip the wrong number"
  defect is never used.

## Set 1 — Data extraction, conformation & ETL build problems (50 tasks)

Fifty task blueprints built from pain points that data-engineering, ETL and data-conformation teams hit in production.
Each one is a real project, a decision that resolves to **one deterministic recommendation**, and a trap that a
competent solver falls into because something documented was overlooked — a key that is *n + 1* columns, a delta file
whose status column was ignored, a calendar with a 53rd week, a crosswalk that is many-to-many, a unit that changed on a
filing date.

Every trap is an **honest-data** trap: the source data are real, correct and documented. Nothing is planted. The
difficulty comes from method selection, grain, time semantics, identity resolution, reconciliation, or a binding
definition the solver must apply as written.

### What is in each file

Every `problems/Pxx_*.md` file has the same twelve sections, so it can be turned into a task directly:

1. **The real-world project** — who is building what, and how it went wrong the first time.
2. **The business decision** — the one deterministic call, plus the written rules (the "standard/method/protocol" memo
   that goes in the task folder).
3. **Why this gets overlooked** — why capable teams miss it in practice.
4. **Input package** — ≥ 10 files, ≥ 3 formats, at least one file with 10,000+ rows, each with source and licence.
5. **Deterministic solution path** — the single correct method, step by step.
6. **The traps** — each wrong path, why it is tempting, and what it does to the answer.
7. **Why the data is honest** — why this is not a retired "planted defect" trap.
8. **Draft task prompt** — prose, the way you would ask a colleague.
9. **Deliverables** — one to three files across data / visual / text / code families.
10. **Where 25+ rubric criteria come from** — the structure of the answer that generates the rubric.
11. **Golden-output checklist** — what a correct answer must contain.
12. **Build notes** — how to scope the slice so the trap actually flips the recommendation, and what to verify.

`problems_index.csv` lists all fifty with domain, objective family, task shape, core technique, trap family and sources.

### Before you ship a task from a blueprint

* **Download and freeze the inputs.** Record source URL, download date, and licence for every file. Several sources are
  live (OpenFEMA, CFPB, NPPES, BDC, AACT, Inside Airbnb); answers change between downloads.
* **Verify every field name, code value and threshold against the documentation you ship.** The blueprints name fields
  and rules as they are documented to the best of current knowledge; agencies rename columns and revise rules. Where a
  blueprint says "verify", treat it as a required check, not a suggestion.
* **Compute both the correct path and each trap path before freezing the prompt.** Section 12 of every file says how to
  pick the slice (state, year, entity set, cap) so the trap changes the recommendation. If it does not flip on your slice,
  change the slice — do not change the data.
* **Write the method memo yourself, from the rules in Section 2.** It is the only authored document in the package; every
  other input should be a real, licence-clean public file.
* **Keep the deliverables to one to three files** and prefer a visual where it lets the stakeholder read the decision at
  a glance.

## Set 2 — Analytical stumps (300 tasks)

Three hundred task blueprints, fifty in each of six analytical categories. Each mirrors a problem that analytics, data-science
and operations teams face at large companies — growth, integrity and ranking metrics at consumer-internet platforms, capacity
and reliability in cloud and networking, yield and supplier quality in hardware manufacturing — and in utilities, healthcare,
finance, transport and the public sector. The header of every file names the company problem it mirrors.

**The stump is always analytical or methodological, never semantic.** The data are real and documented, the rules are written
in a memo, and nothing hinges on reading a field name or a sentence the wrong way. A capable solver who reads everything
correctly still reaches the wrong recommendation by taking a plausible analytical path that is wrong for how the data were
generated. Section 6 of every file lists those wrong paths, and Section 12 says how to choose the slice so that at least one
of them changes the recommendation.

### Recurring stump mechanisms (each task has its own twist)

* **Non-additive statistics treated as additive** — maxima and percentiles of sums (FC02, FC06, DA12, RC44), ratio metrics such
  as DAU/MAU (DA06), harmonic means (DA07), merged histograms (DA08).
* **Censoring, truncation and length bias** — demand capped by capacity (FC01, RC41), open cases (DA02), interval-censored ages
  (DA29), delayed entry (DA10), length-biased snapshots (DA05), right-truncated cohorts (RC12).
* **Composition and mix** — Simpson's paradox (RC33), shift-share (RC17, RC20), denominators and reference points that moved (RC18, RC34),
  trading-day composition (FC26), reporter mix (RC13).
* **Selection and regression to the mean** — winner's curse (OS01, DS11), hot-spot and player regression to the mean (OS03,
  FC22), leaderboard overfitting (DS25), selected trial outcomes (DS16), inspection selection bias (AD46).
* **Leakage and look-ahead** — leaked features (FC04), undeveloped recent cohorts (FC10), real-time data vintages (FC25),

### What is in each file

Every `analytical_tasks/<category>/<ID>_*.md` file opens with a header table — **Category**, **Mirrors** (the company problem it
stands for), **Domain**, **Task shape**, **Core method**, **Analytical stump**, **Primary sources** — followed by twelve sections:

1. **The real-world situation** — who faces the problem and what is at stake.
2. **The decision** — the one deterministic recommendation, plus the rules of the memo that ships with the inputs.
3. **Why capable analysts get it wrong** — the pull of the wrong path.
4. **Input package** — every file with format, approximate rows, source, licence and role.
5. **Deterministic solution path** — the single correct method, step by step.
6. **Wrong paths (method errors, not misreadings)** — what each does to the answer.
7. **Why the stump is analytical, not semantic.**
8. **Draft task prompt** — prose, the way a stakeholder would ask.
9. **Deliverables** — one to three files, usually a table, a chart and a one-page note.
10. **Where 25+ rubric criteria come from.**
11. **Golden-output checklist.**
12. **Build notes** — how to scope the slice so the stump flips the recommendation, and what to verify.

### Uniqueness

* 300 distinct projects. Within Set 2, every task has its own primary dataset; widely used reference series (weather stations,
  census population, price indexes, holiday calendars) recur only as secondary inputs.
* No two tasks share a stump. Where a family recurs (mix vs rate, exposure, censoring), the mechanism, the data and the decision
  differ.
* Two public sources also appear in Set 1 for an unrelated problem: EPA CAMPD (P19 crosswalk; RC10 heat-rate bridge) and BTS
  on-time performance (P26 carrier drill-down; RC34 schedule padding).

### Before you ship an analytical task

* **Freeze the inputs** and record the source URL, download date, licence and checksum of every file. Several sources are live
  APIs; answers change between downloads.
* **Size the package to the input bar** (at least 10 files, 3 formats, one file of 10,000+ rows) with real files the method uses:
  the named sources, their documentation and code lists, and the lookups and calendars the rules need.
* **Verify every field name, code value and threshold** against the documentation you ship. Treat each "verify" in a licence or
  source cell as a required check.
* **Run the deterministic path and every wrong path in Section 6** on the frozen slice, with seeds fixed where the method is
  stochastic. Keep the slice only if at least one wrong path changes the recommendation; if none does, change the slice as
  Section 12 describes — never the data.
* **Write the memo and the stakeholder claim document yourself** from Sections 1–2. They, the provenance manifest and files
  derived deterministically from listed public inputs are the only authored files; every other input is a real public file.
* **Score with the Section 10 rubric** at the target weights: about 30–40% on the recommendation, 5–10% on instruction
  following, about 55% on the supplementary asks.
