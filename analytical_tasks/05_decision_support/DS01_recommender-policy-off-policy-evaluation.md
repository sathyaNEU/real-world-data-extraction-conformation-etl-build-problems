# DS01 — Launching a new recommendation policy: logged clicks evaluate the old policy, not the new one

| Field | Value |
|---|---|
| Category | Decision Support |
| Mirrors | Recommender and ranking teams at e-commerce, streaming and social platforms deciding which policy to ship from logged interaction data before running an A/B test |
| Domain | E-commerce / recommender systems |
| Task shape | 07 · Grid of cells (3 candidate policies × 3 estimators → estimated click-through rate with confidence intervals; the policy shipped to the A/B test) |
| Core method | Off-policy evaluation from logged bandit feedback with known propensities: inverse propensity scoring (IPS), self-normalised IPS (SNIPS) and doubly robust (DR) estimates of each candidate policy's CTR; validation of estimators by evaluating the uniform-random logging data's known ground truth (the dataset's two logging policies) |
| Analytical stump | Averaging clicks on items that a candidate policy *would* recommend, using logs collected by a different policy, ignores that the logs over-represent the logging policy's choices (selection bias). Naive replay estimates favour policies similar to the logger. Correct estimates reweight by propensities and can reverse the ranking |
| Primary sources | Open Bandit Dataset (ZOZOTOWN fashion e-commerce; Saito et al.) |

## 1. The real-world situation

A fashion e-commerce company's recommendation team has three candidate policies for its "all items" carousel. The analyst estimated each
policy's CTR by averaging clicks in the production logs whenever the logged item matched what the policy would have shown, and nominated the
policy that most resembles the current one. The experimentation lead asked for propensity-corrected estimates.

## 2. The decision (one deterministic recommendation)

**The policy sent to the A/B test: highest DR-estimated CTR whose 95% interval lower bound exceeds the current policy's on-policy CTR, or "no
launch" if none does.**

Rules (experimentation memo):

* Data: Open Bandit Dataset "all" campaign; logs from the Bernoulli Thompson Sampling (BTS) policy are the evaluation data; logs from the uniform
  Random policy are the validation data (on-policy ground truth for random).
* Candidate policies: deterministic rankings defined in `candidate_policies.json` (by item features and context; evaluated at position 1 only per
  memo).
* Estimators: IPS, SNIPS and DR (reward model: logistic regression on context × item features per memo, fitted on a held-out 30% split).
* Validation: estimate the Random policy's CTR from BTS logs with each estimator; compare with its on-policy CTR; report relative error.
* Intervals: 95% bootstrap (1,000 resamples, seed 12345).
* Current policy: BTS on-policy CTR from its own logs.
* Launch rule above.

## 3. Why capable analysts get it wrong

* Replay/matching on logged actions looks like a fair comparison.
* The logging policy chooses some items far more often; matched samples are not representative.
* Propensities are recorded in the dataset and are essential.
* IPS variance can be large; SNIPS and DR stabilise; the memo uses DR for the decision.

## 5. Deterministic solution path

1. Load logs; restrict to position 1 per memo; prepare contexts.
2. Fit the reward model; compute IPS, SNIPS, DR for candidates.
3. Validate estimators on the Random policy; bootstrap intervals.
4. Apply the launch rule; contrast with replay estimates.

## 6. Wrong paths (method errors, not misreadings)

**A — replay/matching averages.** Selection bias toward the logger.

**B — ignoring propensities.** Same bias.

**C — DR with the reward model fitted on all data.** Leakage; overconfident.

**D — choosing by point estimate only.** Ignores the interval rule.

## 7. Why the stump is analytical, not semantic

The estimators and rule are specified. The trap is evaluating a new policy on data generated by a different one.

## 8. Draft task prompt (prose)
