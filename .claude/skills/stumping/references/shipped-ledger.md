# Shipped ledger

> **One line per build, recording what the portal said and what each build paid for.** The
> draw-time anti-clone check runs against the fingerprint cards (`../../fingerprint/`), not this
> file: a card exists for every build on disk from the moment its draw is fixed. Read this file for
> outcomes and for the lessons below the table.
>
> **Writing a row.** A row goes in when the author reports the portal result, and
> at no other time. Not when the draw is fixed, not when the build is finished, not when the
> submission is written. The author says the task stumped (or did not) after testing it on the
> official portal, and that report is what a row records. Until then the build is in flight and this
> file does not know about it.
>
> **And a row is rewritten in the same edit as the abandonment of the version it describes.** A row
> that describes a dead version is worse than a missing row, because the pattern ban runs against it
> and passes: task89's row still described its banned v3 when the next build drew, so
> `G11 binding_constraint` read as unused while the previous reported build had carried its decisive
> rung on it.
>
> **What that costs, and what covers it.** Builds finished but not yet reported are invisible here,
> so this file cannot carry the draw-time bans. The fingerprint cards cover that gap: a card is
> filed when a build's draw is fixed and `guard.py check` runs the bans against every card, so
> consecutive builds cannot collide unseen. A card records what a build **is**, never what the
> portal said, which is why it is not the pending row this rule forbids. Do not paper over the gap
> here with a pending row. A row written before the portal has spoken records a guess as a fact.
