## Three rules

- Task type: metric-definition-measurement-science (Product Analytics): a counterfactual on a measured web metric,
  Largest Contentful Paint, built load by load from its RUM attribution parts, the page's first contentful paint and
  the server HTML each page is sent with.
- Domain test: the deciding quantity is the page loads a month a hero-image playbook brings under the 2,500 ms LCP
  line, which web performance engineers estimate from RUM attribution by moving each part of the paint the way the
  change moves it and keeping what it cannot reach: a preload from the document head can only fetch an image the
  server HTML names, so on a page whose hero is put in by client-side code the request still starts when that code
  runs, and the largest paint never comes before the page's first paint.
- Swap: "where a hospital sends its patient-flow team, the clinic whose fast-track brings the most visits under four
  hours" loses what decides here: there is no paint split into parts, no preload that can only fetch what a document
  names, no server-rendered page against a client-rendered one and no first paint a page cannot beat, so neither the
  reach nor the floor stands for anything and the property ranking cannot be built.
- Layer 1: RUM sampling rates set per origin in an effective-dated configuration and changed mid-month for two
  properties (the collector's quota reviews); the extract cut on whole UTC days around a Sydney-time month (the RUM
  warehouse's day partitions); beacons the collector received twice; navigation types (back-forward cache restores
  with no LCP, prerendered loads timed from activation, from the web-vitals library); image hosts of three kinds per
  property beside agency, advertising and video hosts; the review windows by Sydney date across daylight-saving
  changes; the crawl taken on the night of 2 December in UTC; CrUX rows by origin and form factor beside the group's
  own RUM; analytics page views at another grain; and, on the ask paths only, the image hosts' hourly rollups in UTC
  with every slot size and revalidations, the legacy aliases logged by the old media server on its own clock, a DAM
  export with three renditions an asset, library records kept beside migrated assets, retired assets, and each asset
  filed under the collection it was uploaded to.
- Layer 2: estimand identification, the counterfactual paint: each slow own-image load is carried through the
  playbook part by part, the delay at the level the engagements settled at only where the preload can reach the hero
  (the page's server HTML carries it, by the crawl), the delay as it is where it cannot, and every paint floored at the
  load's own first contentful paint.
- Decisive step: recognising that the engagements validated the playbook only on pages whose server HTML carried the
  hero, and that the preload cannot reach a hero a client-side app puts on the page, so each load's reach is read from
  the crawl of its page's server HTML before the engagements' effect is carried onto it.
- Not semantics: every field, host, sampling rate, first paint and crawl row read correctly, and every load kept
  exactly right, still leaves open whether the engagements' measured effect applies to every own-hero load; no field,
  code or definition says which pages are apps or that a preload needs the hero in the HTML, and the crawl's rows are
  plain image lists that say nothing about reach.
- Not rule application: the charter files what is counted and the squad's scope, and the change log what the playbook
  does; no rule says which loads the preload reaches or how an engagement's effect transports, so executing every
  filed sentence leaves the reach open. Enumerated family: the effect carried onto every own-hero load (6.3 million at
  Matchday) or only onto loads whose page's server HTML carries the hero (Trailhead 4.9); standing family: the reach
  read by page or anywhere in the crawl, and an unreached hero's load time at 0, 0.48 or 1 times today, which agree to
  the unit on every rounded count (a spread of exactly zero inside the standing family, against 2.9 million on
  Matchday between the families); the ruling-out is silent: no clause, column or engagement names it, only the join
  of each load to its page's crawl rows.
- Analyst test: a strong analyst who weights the beacons to page loads, keeps the slow own-image loads, splits each
  paint into its four parts, carries the engagements' delay level and load time ratio onto every one of them and
  floors each paint at its own first contentful paint (the construction both portal responses reached) files
  Matchday, 6.3 million page loads a month; ratios of medians or the preload rule of thumb file Ledger (8.8 and 9.7
  million); the level with the render delay held files Pantry (8.0 million); only the reach read from the crawl files
  Trailhead.
- Estimand: the squad charter (`performance_squad_charter_2026.pdf`, 2.1 to 2.4): the property where the playbook
  will move the most page loads a month into the good LCP band (2,500 ms or less), counted on the group's RUM for the
  latest complete calendar month in Sydney time, a page load being a navigation that reports LCP and a sampled load's
  beacon standing for the page loads its rate represents, a load moved being one slower than 2,500 ms in that month
  that would have been 2,500 ms or less with the playbook in place, the playbook reaching the loads whose LCP element
  is the property's own hero image.
- No decoy: nothing is planted: no memo, briefing or stakeholder figure argues for a property; the crawl is the
  group's own nightly crawl of its pages and states nothing about the squad; the app sections are named in no file and
  visible only as pages whose server HTML carries the logo alone; charter 3.2 states the squad's scope truly and the
  golden cites it.
- No certified replay: no file states any engagement's, page's or property's LCP after the playbook, so no model is
  chosen by reproducing a certified figure; the engagements' beacons and the crawl are raw evidence.
- Lesson: an intervention validated on past applications carries only as far as its mechanism can act, and the past
  applications cannot show where that is when every one of them met the precondition: the counterfactual is built
  with each unit's own precondition read from a record of how the unit is actually served, which the validated
  effect's back-test never needed and therefore never tested; no build on file carries an intervention's validated
  effect onto units its mechanism cannot reach.
